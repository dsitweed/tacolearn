## 1. Authentication & Authorization

### 1.1 Authentication Mechanism

**JWT (JSON Web Tokens)**
```
Token Structure: Header.Payload.Signature

Header: {
  "alg": "HS256",
  "typ": "JWT"
}

Payload: {
  "sub": "user_id",
  "role": "STUDENT",
  "email": "student@example.com",
  "iat": 1234567890,
  "exp": 1234654290  // 24 hours
}

Signature: HMAC-SHA256(base64(header) + "." + base64(payload), SECRET_KEY)
```

**Token Generation**
```
1. User logs in with email/password
2. Backend validates credentials
3. Generate access token (24 hours)
4. Generate refresh token (7 days)
5. Store refresh token in database
6. Return tokens in HttpOnly cookies
```

**Token Refresh Flow**
```
Access Token Expired
        ↓
Client sends refresh token to /auth/refresh
        ↓
Backend validates refresh token
        ↓
Generate new access token
        ↓
Return new token in cookie
```

### 1.2 Authorization (RBAC)

**Role-Based Access Control**
```
STUDENT
├─ Can access: own dashboard, own learning data
├─ Cannot access: teacher dashboard, admin panel
└─ Endpoints: /students/*, /practice/*, /srs/*

TEACHER
├─ Can access: assigned classes, student progress
├─ Cannot access: admin panel, other teachers' classes
└─ Endpoints: /teachers/*, /classes/*

ADMIN
├─ Can access: all user data, system settings
├─ Cannot access: student learning data (privacy)
└─ Endpoints: /admin/*
```

**Guard Implementation**
```typescript
@UseGuards(AuthGuard('jwt'), RoleGuard)
@Roles(UserRole.TEACHER, UserRole.ADMIN)
@Get('/classes')
getClasses(@CurrentUser() user: User) {
  // Only TEACHER and ADMIN can access
}
```

### 1.3 Password Security

**Password Requirements**
- Minimum 12 characters
- Must contain: uppercase, lowercase, number, special character
- Cannot be common passwords (checked against dictionary)
- Cannot contain username or email

**Password Storage**
```
1. Receive plaintext password
2. Generate salt: bcrypt.genSalt(10)
3. Hash: bcrypt.hash(password, salt)
4. Store hash in database
5. Never store plaintext password
6. Never log passwords
```

**Password Reset**
```
1. User requests password reset
2. Generate secure token (crypto.randomBytes(32))
3. Hash token and store in database (expires 1 hour)
4. Send email with reset link
5. User clicks link, verifies token
6. Set new password
7. Invalidate all active sessions
```

## 2. Data Protection

### 2.1 Encryption in Transit

**HTTPS/TLS**
- All communication encrypted with TLS 1.3
- Certificate management via Let's Encrypt
- HSTS header: `Strict-Transport-Security: max-age=31536000`
- Cipher suites: Only strong algorithms (TLS_AES_256_GCM_SHA384, etc.)

**API Communication**
```
Frontend (HTTPS)
    ↓
Load Balancer (TLS termination)
    ↓
Backend (HTTP, internal network only)
```

### 2.2 Encryption at Rest

**Database Encryption**
- PostgreSQL: Native encryption at tablespace level
- Fields encrypted: passwords, personal identifiers
- Column-level encryption for sensitive data

**Sensitive Fields Encryption**
```typescript
// Example: Encrypt student identifiers
class Student {
  @Encrypt()
  @Column()
  idCardNumber: string;  // Encrypted in DB
  
  @Column()
  email: string;  // Hashed
}
```

### 2.3 Data Classification

| Classification | Data | Storage | Access |
|---|---|---|---|
| **Public** | JLPT level, general progress | Plain text | Anyone |
| **Internal** | Learning patterns, weak areas | Encrypted | Student + Teacher |
| **Sensitive** | Email, identifiers | Hashed | Student + Admin |
| **Restricted** | Passwords, payment info | Encrypted + Hashed | Admin only |

## 3. API Security

### 3.1 Input Validation

**Request Validation**
```typescript
// DTO with class-validator
export class CreateQuestionAnswerDto {
  @IsUUID()
  questionId: string;
  
  @IsIn(['A', 'B', 'C', 'D'])
  answer: string;
  
  @IsInt()
  @Min(0)
  @Max(300)
  timeSpent: number;
}

// Automatic validation by NestJS pipes
```

**SQL Injection Prevention**
- Use Prisma ORM (prepared statements)
- Never concatenate user input into SQL
- Example:
  ```typescript
  // SAFE - uses parameterized query
  await prisma.student.findUnique({
    where: { email: userEmail }
  });
  
  // UNSAFE - never do this
  await db.query(`SELECT * FROM students WHERE email = '${userEmail}'`);
  ```

### 3.2 Cross-Site Scripting (XSS) Prevention

**Content Security Policy (CSP)**
```
Content-Security-Policy: 
  default-src 'self';
  script-src 'self' 'unsafe-inline' cdn.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' https:;
  font-src 'self' fonts.googleapis.com;
  connect-src 'self' api.tacolearn.com;
  frame-ancestors 'none';
```

**HTML Sanitization**
```typescript
import DOMPurify from 'dompurify';

// Sanitize user-generated content
const sanitized = DOMPurify.sanitize(userContent);
```

### 3.3 Cross-Site Request Forgery (CSRF) Protection

**CSRF Tokens**
- Generate CSRF token for each session
- Validate on state-changing requests (POST, PUT, PATCH, DELETE)
- Token in header: `X-CSRF-Token`

**SameSite Cookies**
```
Set-Cookie: accessToken=...; SameSite=Strict; Secure; HttpOnly
```

### 3.4 Rate Limiting

**Implementation**
```typescript
@UseGuards(ThrottleGuard)
@Throttle(100, 60)  // 100 requests per 60 seconds
@Post('/auth/login')
login(@Body() credentials: LoginDto) {
  // Rate limited endpoint
}
```

**Per-User Limiting**
```
API Key/User ID
      ↓
Redis counter: `rate_limit:{userId}:{endpoint}`
      ↓
Increment on request
      ↓
If > limit, return 429 Too Many Requests
```

## 4. Secrets Management

### 4.1 Environment Variables

**Sensitive Secrets**
- Database credentials
- JWT secret key
- API keys (Stripe, SendGrid)
- Redis password
- AWS/Cloud credentials

**Storage**
- Never commit to git (use .gitignore)
- Use `.env` file (dev only)
- Use environment variable injection (production)
- Vault service for sensitive data (future)

**Example .env.example** (check into git, no actual secrets)
```
DATABASE_URL=postgresql://user:password@localhost/dbname
JWT_SECRET=your_jwt_secret_here
REDIS_URL=redis://localhost:6379
STRIPE_API_KEY=sk_test_...
```

### 4.2 Key Rotation

**JWT Secret Rotation**
```
1. Generate new secret
2. Keep old secret active for 30 days
3. Accept tokens signed with either secret
4. Regenerate tokens with new secret
5. After 30 days, only accept new secret
```

## 5. Application Security

### 5.1 Dependency Management

**Security Scanning**
```bash
npm audit                 # Scan for vulnerabilities
npm audit fix             # Auto-fix low/moderate vulnerabilities
dependabot               # Automated dependency updates
snyk                     # Continuous security scanning
```

**Dependency Policy**
- Update all critical vulnerabilities immediately
- Update high vulnerabilities within 7 days
- Review and update medium/low regularly

### 5.2 Error Handling

**Production Error Messages**
```typescript
// SAFE - Generic error message
throw new BadRequestException('Invalid credentials');

// UNSAFE - Leaks system information
throw new BadRequestException(
  `User with email ${email} not found`
);
```

**Logging**
```typescript
// Log errors internally (server logs)
logger.error('Database connection failed', {
  error: err,
  timestamp: new Date(),
  userId: user?.id
});

// Send generic message to client
return {
  status: 'error',
  message: 'An unexpected error occurred'
};
```

### 5.3 Helmet Security Headers

```typescript
import helmet from '@nestjs/helmet';

app.use(helmet());
// Sets security headers:
// - X-Content-Type-Options: nosniff
// - X-Frame-Options: DENY
// - X-XSS-Protection: 1; mode=block
// - Strict-Transport-Security: max-age=31536000
// - Content-Security-Policy: ...
```

## 6. Data Privacy & Compliance

### 6.1 GDPR Compliance

**Data Collection**
- Collect only necessary data
- Inform users what data is collected
- Obtain explicit consent before processing

**User Rights**
- **Right to Access**: User can download their data
- **Right to Erasure**: "Right to be forgotten"
- **Right to Data Portability**: Export data in standard format
- **Right to Restrict Processing**: Pause data usage

**Implementation**
```typescript
// GDPR: User data export
@Get('/me/export')
async exportUserData(@CurrentUser() user: User) {
  return {
    personal: { email, name, ... },
    learning: { attempts, mastery, ... },
    preferences: { ... }
  };
}

// GDPR: User data deletion
@Delete('/me')
async deleteAccount(@CurrentUser() user: User) {
  // Anonymize user data
  // Keep only aggregate learning statistics
  await deletePersonalData(user.id);
}
```

### 6.2 Data Retention

| Data Type | Retention Period | Reason |
|---|---|---|
| Learning attempts | 7 years | Legal requirement for education |
| Personal info | Until account deletion | User management |
| Access logs | 90 days | Security audit trail |
| Email backups | 30 days | Compliance |
| System logs | 30 days | Troubleshooting |

### 6.3 Data Sharing

**Third-party Integration**
- Stripe (payment): Only credit card info, never stored locally
- SendGrid (email): Only email content, anonymized
- Socket.IO: Only session data, no personal info

**User Consent**
```
Before sharing data with third party:
1. Show privacy notice
2. Get explicit consent
3. Document consent timestamp
4. Allow opt-out anytime
```

## 7. Monitoring & Incident Response

### 7.1 Security Monitoring

**Log Aggregation**
```
Application Logs
  ├─ Error logs
  ├─ Access logs
  ├─ Audit logs
  └─ Security events
        ↓
    ELK Stack (Elasticsearch, Logstash, Kibana)
        ↓
    Analyze & Alert
```

**Alerts**
- Multiple failed login attempts
- Unusual API access patterns
- Database errors
- Missing CSRF tokens
- Invalid JWT tokens

### 7.2 Security Testing

**Automated Testing**
- OWASP dependency scanning
- SAST (Static Application Security Testing)
- Container scanning (Docker images)
- API security testing

**Manual Testing**
- Quarterly penetration testing
- Code security review
- Infrastructure security audit

## 8. Incident Response Plan

### 8.1 Security Incident Types

1. **Data Breach**: Unauthorized data access
2. **System Compromise**: Malware/backdoor detected
3. **DDoS Attack**: Service unavailable
4. **Account Compromise**: Unauthorized login
5. **Configuration Error**: Security misconfiguration

### 8.2 Response Steps

```
Detection
    ↓
Assessment (impact, severity)
    ↓
Containment (isolate affected systems)
    ↓
Investigation (root cause analysis)
    ↓
Remediation (fix vulnerability)
    ↓
Notification (inform affected users if needed)
    ↓
Post-Incident Review (lessons learned)
```
